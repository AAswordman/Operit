# 实现与调查

## 重试状态标签

`EnhancedAIService.sendMessage` 的非致命错误回调将状态设为 `Connecting`，`MessageProcessingDelegate.keepRequestUiAlive` 同时把该状态映射到当前对话。此前普通回复仅在 `isFirstChunk` 为真时切换到 `Receiving`，中途重试后该标记已经为假；工具后续回复仅在开始收集流之前设置接收状态，也不会在中途重试后恢复。后续工具状态变化因而可能成为下一次覆盖重试提示的时机。

两处响应收集现在都独立检查非空片段及当前连接状态。满足条件时在主线程再次核对状态，然后切换为“正在接收AI响应”或“正在接收工具执行后的AI响应”。状态已为接收中时不重复写入；首块计时仍只记录一次，子任务仍不修改主对话状态。主线程内再次检查连接状态，避免已经切换为错误、停止或执行工具的状态被覆盖。

本轮修改局限于 `EnhancedAIService.kt` 的这两个收集回调，不改变错误传播、重试次数、保存点、回滚事件或输出文本。

## 显示与行为转场

`AppContent` 的外层 `Scaffold` 根据当前路由立即切换顶部栏；`GlobalDisplaySettings` 使用页面内部标题栏，因此它会立即隐藏外层顶部栏。此前跨页动画又将离开的设置首页保留到淡出结束，退出中的首页于是按已移除顶部栏后的 `innerPadding` 重新排版。开启导航动画时该重叠可持续约 280 毫秒。

`Screen.GlobalDisplaySettings` 现在设置 `participatesInCrossfadeTransition = false`。现有导航状态机在导航变更的同一轮渲染就不再选取旧页面作为过渡内容，进出该页均直接切换，不会让首页与显示页面共用已变化的宿主留白。页面自己的标题栏、系统栏留白、返回处理和偏好保存流程保持现有实现，其他页面的导航动画不受该路由标记影响。

## 错误发生时的输出处理

调查范围是当前 Android 源码中的 OpenAI、Claude、Gemini 请求路径、公共重试入口以及聊天消息保存路径；本轮没有用真实故障请求或代理注入故障执行运行验证，不能据此断言某一次用户遇到的具体故障类型。

5000 系列由 `ApiTransportError` 为传输故障生成描述。DNS、连接超时、HTTP/2 流重置、连接中止、首 Token 超时、TLS 失败及连接失败分别使用 5000、5001、5002、5003、5004、5005、5006。这段错误描述代码不处理回答正文。

### 决定继续重试

公共入口 `handleKeyAwareRetry` 先判断能否重试以及密钥选择，再在重试被接受时执行 `onRetryAccepted`，然后发布错误提示并等待下一次尝试。OpenAI、Claude、Gemini 都把该回调接到本次请求起点的 `ROLLBACK` 事件。`EnhancedAIService` 和聊天流收集器按保存点同步截短缓冲、当前轮次及显示中的文本。

因此，已经显示的半截回答在重试开始时消失，是现有实现明确执行的撤回策略。它的目的是避免把失败尝试的半截输出与下一次从头生成的回答拼成一条正文。它撤回的是当前这次模型请求，不是此前已经完成的工具轮次或聊天历史；也不是只要出现一个 5000 系列数字就按字符数裁剪。

源码依据：

- `api/chat/keypool/ApiKeyRequestSupport.kt` 的 `handleKeyAwareRetry`
- `api/chat/llmprovider/OpenAIProvider.kt` 的请求保存点及 `emitRollback`
- `api/chat/llmprovider/ClaudeProvider.kt`、`GeminiProvider.kt` 的同类保存点与回调
- `util/stream/TextStreamRevisionTracker.kt` 的 `rollback`
- `services/core/MessageProcessingDelegate.kt` 的 `TextStreamEventType.ROLLBACK` 分支

### 终止重试或关闭重试

`handleKeyAwareRetry` 在重试关闭、策略要求停止或重试耗尽时直接抛错，不执行该次 `onRetryAccepted`。消息处理层按请求失败收尾，保存最后一次尝试仍留在缓冲中的部分输出；前面几次重试时已经撤回的片段不会自动恢复。因此，如果前一次尝试输出较多、最后一次尝试没有输出，最终可见内容仍会比用户之前看到的少。

源码依据是 `MessageProcessingDelegate` 的 `terminalFailure`、`shouldFinalizeInterruptedMessage`、`detachStreamingAiMessage` 和 `resolveFinalContent`。以上是源码行为核对，不代表已经做过数据库或实机故障回归。

### 可改善部分与限制

连接中断后，当前实现会用请求历史重新生成；这三条路径没有通用的服务端断点续传机制，不能保证新回答逐字接上已经接收的内容。直接保留旧片段再追加新结果，会形成重复或矛盾的正文，工具调用参数也可能重复或不完整。

界面策略可以改善，例如等新的尝试真正开始输出后再替换旧片段，或者单独保留失败尝试的记录。这些都需要同步定义最终保存的正文、工具调用是否可执行以及取消时保留哪一次输出，属于另一项行为调整。本轮只调查，不实施该策略变化。

另外，`ApiTransportError.description` 会对错误 JSON 的 `detail` 使用 `take(500)`，限制的是异常详情的长度，与 AI 回答正文无关。工具结果过长时的独立限制同样不是由 5000 系列错误码触发。
