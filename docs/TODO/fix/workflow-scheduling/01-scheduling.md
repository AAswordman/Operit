# 调度规则与迁移

## 时间标准

- 固定间隔以启用或修改计划为起点，首次等待完整间隔，最少 15 分钟。持久请求保留毫秒值，不静默截成整分钟；修改名称、描述、节点坐标及执行统计不重置等待。
- 五段 Cron 按系统当前时区的日历匹配，秒为零，始终计算严格晚于当前时刻的下一次。支持通配符、列表、范围、步进、月份和星期英文简称，星期日支持 0 或 7。日与星期均限定时采用或关系；含通配符时保留字段交集约束。每周和工作日模板可实际执行。
- 指定时间支持严格本地日期时间与带偏移的 ISO 时间。开启重复时，从所选日期起每天按该当地时间运行；不存在的夏令时时刻不执行，重复的一小时中每日指定时间只取一次。关闭重复仅运行一次。Cron 则按实际时间线匹配，可匹配夏令时回拨的两个同名分钟。
- 截止时间包含边界，执行开始前和串行队列等待结束后都检查，超过截止后不再开始执行。错过多个 Cron 时刻后不会补跑全部历史次数。

## 请求与恢复

`WorkflowSchedulePlan` 以触发节点 ID、定时类型和现有定时配置生成签名。请求保存签名与计划时刻；排队期间停用、删除节点或修改计划后，旧请求不再执行业务。WorkManager 工作名继续使用 `workflow_<id>`。

间隔重复使用周期请求，其余计划使用一次性请求。日历重复执行后按当前时区追加下一次，已记录的业务失败不会中断后续重复；运行环境尚未就绪时保留 WorkManager 重试。错误基础设施调用也保留重试，取消继续传播。

应用冷启动和设备重启只恢复缺失计划，保留有效及正在执行的请求。旧周期请求迁移尽量保留 WorkManager 登记的下一次时间；正在运行的旧请求在业务结束后迁移。一次性计划的消费状态按工作流和计划签名持久保存，不依赖 WorkManager 已完成历史的保留时长；用户重新启用或修改计划时可重新安排。系统时间或时区变化只重算日历任务，不重置间隔计时，也不取消正在执行的任务。

下一次时间读取已登记请求，而不是每次查询都用现在加间隔。日志记录登记计划时刻、系统派发时刻与串行队列放行后的开始时刻，便于区分时间计算、系统派发和队列等待。

## 系统边界

仍使用 Android WorkManager。15 分钟是固定间隔的最小配置，不代表准点保证；休眠、省电、后台限制、系统配额和已有串行队列都可延后实际执行。强行停止应用后需重新打开恢复调度。没有新增精确闹钟权限或承诺秒级触发。

本轮仍按既有行为安排第一个 schedule 触发节点，不扩展多定时节点并发。配置界面与仓库共用计划校验，不再把非法规则静默改成另一种间隔；已有低于 15 分钟的无效配置需要改为有效值。

实现与回归用例编写 [DONE]。31 项 JVM 用例由仓库 Android Tests 执行，冷启动、迁移与系统事件由完整设备清单验收。
