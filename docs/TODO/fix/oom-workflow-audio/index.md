# 工作流并发、总结与语音条内存排查

用户报告两个工作流同时执行，以及总结或插件语音条输出时容易发生 OOM。语音条为插件注册的自定义 XML，可点击播放实际 WAV 文件。本轮分别追踪工作流调度、总结准备及响应收集、语音条文件资源读取和播放生命周期。

## 事实与边界

- 当前基线为 `d3d130ea`，开始排查时工作区干净
- 已取得 `com.operit.voice_bar` 的 `0.5.5-four-provider-voice-library` 插件包，解压后确认语音条通过每个实例的 WebView 和 HTML `<audio preload="metadata">` 直接播放 `file://` 文件
- 尚未取得反馈设备的 OOM 堆栈、堆转储及出问题的两个工作流，不能把静态发现直接认定为原始崩溃的唯一原因
- 发现宿主 Compose DSL 的 `actionStore` 只新增回调、没有随重绘回收旧回调；语音条展开收起确实使用这条路径，本轮补充按已提交界面回收回调的修复
- 普通总结入口会去掉标准模型媒体链接；自定义 WAV 引用不会因为扩展名自动触发文件加载
- 源码能确认的重复复制和整文件缓冲可独立修正，但不能据此宣称两个反馈入口的根因均已复现或 OOM 已彻底解决

## 最小修复范围

1. 工作流节点结果继续完整传递，执行日志仅保留固定长度预览，消除日志对完整结果的再次复制和长期持有
2. 总结进度直接检索响应缓冲，避免每个输出片段都构造完整响应字符串
3. 插件 WebView 的非 HTML 文件响应、本地网页服务及 HTTP 改写响应交付输入流，避免先读完整 WAV 到 Java 堆；保持 HTML 注入及已有资源协议
4. 插件引擎仅将执行参数序列化到执行消息一次，不再为计时指标重复生成完整参数 JSON
5. 按已提交的 Compose DSL 界面版本回收旧回调，保留缓存节点、排队事件和独立 WebView 接口所需回调，阻止回调表随重绘持续增长
6. 不调整工作流队列覆盖范围，不重写播放器实现，不改变媒体池、聊天消息及插件现有调用方式
