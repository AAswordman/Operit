# 定位与修复

## 结论边界

本轮完成源码追踪及可独立确认的内存放大修复，没有取得反馈设备的崩溃堆栈或复现两个原始 OOM。下面的“已确认”指确定存在的代码行为，不等于已经证明它就是某次崩溃的唯一原因。

## 工作流并发

`WorkflowRepository.triggerScheduledWorkflow` 使用 `ScheduledWorkflowQueue` 的进程内互斥锁，等待中的定时任务仅保留调用状态，进入队列后才执行 `triggerWorkflow` 和读取完整工作流。两个定时任务从这个入口进入时，完整执行不会同时发生。

手动执行通过 `WorkflowViewModel -> triggerWorkflowWithCallback`，工具调用通过 `StandardWorkflowTools -> triggerWorkflow`，不经过上述队列。运行任务登记只排除同一 workflow ID 的重复执行，不排除不同工作流同时运行。因此已有队列可以降低两个定时执行的重叠峰值，但没有为所有入口或单次执行建立内存预算。

`WorkflowExecutor.executeTopologicalOrder` 顺序执行节点。图的可达性遍历有访问集合，DFS 环检测有访问状态；没有发现同一图因环而无限执行的路径。节点可调用其他工作流，当前未取得触发崩溃的工作流图，不能排除业务节点间的互相触发或大输出扩展。

### 已修复的重复持有

此前成功节点的完整结果同时存在于 `nodeResults`，以及 `getString(workflow_log_node_success, ..., resultMessage)` 生成的另一份日志字符串中。执行日志一直保留到整个工作流结束，之后又参与执行记录 JSON 序列化。仓库默认状态回调还会把 `Success(result)` 再次整体格式化为日志，AppLogger 自身的后续截短无法避免这次完整字符串构造。

现将成功结果的日志输入限制为 800 字符，与执行记录已有 `resultSummary` 长度一致。真正写入 `nodeResults` 和传给 UI 状态回调的仍是完整结果，下游节点的引用、条件、提取结果不变。执行历史日志中不再展示完整节点正文，使用者会看到结果预览；这是一项明确的日志展示变化。

修改位置：`core/workflow/WorkflowExecutor.kt`、`data/repository/WorkflowRepository.kt`。

## 总结及插件参数

`AIMessageManager.summarizeMemory` 去掉标准的模型图片、音视频链接，并整理文字作为总结输入。语音条自定义 XML 中的 WAV 路径只是文字引用时，不会因为扩展名为 WAV 就读取文件。`ConversationService` 的总结准备与响应收集也没有调用语音播放。当前源码不支持“总结一定会把语音文件全部加载”的结论。

### 已修复的响应复制

此前 `ConversationService.generateSummaryFromPromptTurns` 每收到一块内容都为进度匹配执行 `contentBuilder.toString()`。如果一段摘要分多块到达，就会重复分配长度不断增长的整段字符串。现在进度匹配器接受 `CharSequence`，直接检索同一个缓冲；阶段名称、进度值、分片跨界匹配及最终摘要内容保持原逻辑。

### 已修复的参数序列化

`JsEngine.executeScriptFunction` 此前先生成 `paramsObject.toString()`，再把同一个参数对象序列化到 `executionArgsJson`。第一份完整参数 JSON 只用于计时日志的长度，而且即使对应日志关闭也会创建。总结 Hook 可能携带长聊天历史，因此这会增加不必要的峰值分配。

现仅保留实际执行所需的参数序列化；计时日志改记顶层参数键数，执行协议、参数内容、函数调用和会话清理不变。该修改同样作用于工作流调用插件及 XML 渲染 Hook。

修改位置：`core/chat/context/ConversationService.kt`、`core/tools/javascript/JsEngine.kt`。

## WAV 文件读取与播放

已取得 `com.operit.voice_bar` 的 `0.5.5-four-provider-voice-library` 实现。插件将 `<voice>` 转为 Compose DSL，每条语音创建一个 WebView，通过 `<audio preload="metadata">` 直接播放 `file://` 音频文件。没有主动完整读取 WAV、调用 `decodeAudioData` 或创建 Java MediaPlayer。实际播放不经过下述宿主资源回调、本地服务器或媒体池，因此通用输入流修复不能作为这份插件 OOM 已解决的证据。

### 已修复的整文件缓冲

- `ToolPkgComposeDslWebView.buildComposeDslWebResourceResponse` 的 `filePath` 响应曾对非 HTML 文件执行 `readBytes`，再包成 `ByteArrayInputStream`。现在直接提供文件输入流，WebView 负责消费及关闭；构造响应失败时主动关闭文件
- `fetchComposeDslRewrittenResource` 曾把整个 HTTP 响应读入数组后关闭连接。现在提供网络输入流，关闭响应流时同时断开连接，构造失败和准备失败均清理连接。响应状态、响应头、请求方法和请求头继续传递
- `LocalWebServer.serveFileFromDisk` 曾把完整音视频文件读入数组。现在返回定长文件响应流，长度取自已打开文件的 channel；响应构造失败则关闭文件，正常完成或中断由 NanoHTTPD 响应关闭流

文本、Base64 和需注入脚本的 HTML 响应继续按各自协议处理。没有新增播放器、改变音频编码或增加音频文件大小限制，也没有增加新的错误回退。

修改位置：`ui/common/composedsl/ToolPkgComposeDslWebView.kt`、`ui/features/conversation/workspace/preview/LocalWebServer.kt`。

### 生命周期核对

标准 `MarkdownAudioRenderer` 和 `AudioAttachmentPlayer` 已有播放器释放。实际插件使用的 XML Compose DSL 渲染器会归还引擎租约，宿主 WebView 离开组合时停止加载、清空页面并销毁；同一 WebView 的 `remember` 不因每次脚本重绘而必然重建。源码没有发现音频文件递归指回 XML 的加载路径，也没有发现插件注册总结 Hook。

确认了另一条持续持有路径：`JsComposeDslBridge.createContext` 的 `actionStore` 在每次渲染 `onConsoleMessage` 等函数属性时增加回调，原实现没有随重绘删除旧回调。语音条的展开收起会触发重新执行 `Screen`，因此该问题确实覆盖此插件，并会在引擎仍存活时不断保留旧闭包。它是明确的资源累积缺陷，但不是原始 OOM 的设备复现结论。

本轮新增渲染上下文、版本和回调计数快照，在 Compose 提交新树后回收旧树回调。当前树、子节点、插槽、修饰符、状态及 memo 中缓存节点的回调继续保留；尚未提交的新结果和已登记的待执行事件不会被提前删除。WebView 控制器独立注册的接口回调不属于树回收范围。旧上下文或迟到版本的确认不会清理新界面。普通插件页面、弹窗和 XML 语音条均接入相同回收流程；桌面组件的短期引擎仍按现有 finally 销毁。

修复位置：`JsComposeDslBridge.kt`、`JsComposeDslRuntimeScript.kt`、`JsEngine.kt`、`ComposeDslActionRetention.kt`、`ToolPkgComposeDslParser.kt`、`ToolPkgComposeDslActions.kt`、`ToolPkgComposeDslScreen.kt`、`XmlRenderPluginRegistry.kt`。内部渲染响应增加回调快照，不要求插件改接口或重新打包。详细路径和独立插件问题见[源码审阅](04-语音条插件源码审阅.md)。

## 其他已识别风险，尚未改动

`MediaPoolManager` 按条数缓存完整 Base64，默认 12 条，每条原始音视频允许到 20 MiB。极限情况下仅 Base64 字符数据量就约 320 MiB，另有文件读取数组、编码临时数组、JSON 和请求正文；实际堆占用依赖运行时字符串存储。磁盘预加载会重新读入内容。这属于较高的缓存驻留和分配峰值，尚未证明反馈语音条进入该池。

`ImagePoolManager` 先完整解码图片，再做方向修正和 2048 长边限制。高像素原图可能在缩小前就分配很大的 Bitmap；不能用最终尺寸证明入池峰值很小。

上述缓存有条数边界，不能简单写成无限泄漏。改变缓存预算、磁盘淘汰规则或图片解码采样需要分别处理数据保留和图片输出语义，本轮没有混入这类策略修改。
