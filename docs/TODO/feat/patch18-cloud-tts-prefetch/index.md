# 云端 TTS 分句并行预取

## 核查结论

聊天页的手动朗读会把清理后的文本分句，并逐句等待 TtsService.speak 返回；返回值代表该句完成播放，所以后面的云端请求会延迟到前一句播完。悬浮全屏语音的 enqueueSpeak 也通过 previousJob.join 等待前一句结束。

OpenAI HTTP 与 Realtime 原来把请求和播放放在同一个 playbackMutex 中。自定义 HTTP 及其 MiniMax、MiMo、豆包适配器使用请求与播放分开的队列，但合成消费者只有一个；硅基流动也只有一个请求消费者。这些实现没有做到首句准备后并行提交所有已知后句。聊天流式自动朗读已能提前提交文本，不能把所有入口都描述为完全相同的串行行为。

此前的本地修正在独立语音 PR #86 中，只让 Sherpa 在当前句播放时预合成下一句，不是同时合成所有本地分句。本轮不复制该 PR 的改动，也不改变本地模型或系统 TTS 的合成策略。

## 本地实现

新增 api/speech/tts/prefetch 包，OrderedTtsPrefetchQueue 先准备首句，首句音频就绪后放行当前已知的全部后句；之后流式到达的新分句可立即预取。合成使用独立任务，唯一播放消费者按文本提交顺序等待结果，后句先返回不会抢播。完整文本由 QueuedTtsPlayback 沿用 TtsSegmenter 分句，没有增加句号延迟、重试或静音裁剪。

所有已知后句都会加入预取任务，实际同时发出的网络请求仍受网络客户端和云端并发额度约束。首句不会为了等待整段音频而延后播放，下一句尚未返回时仍需等待它。该改动减少应用串行调度产生的空档，不承诺实际播放完全无停顿。

HTTP、OpenAI HTTP、Realtime、硅基流动接入同一个顺序播放与预取队列。MiniMax 和 MiMo 通过 HTTP 委托接入，豆包通过继承 HTTP 实现接入；原有音色、模型和请求参数继续传递。硅基流动保留原有预置与 speech: 自定义音色校验，JSON 请求体使用结构化序列化。Realtime 每句独立持有连接、响应结果与 PCM 缓冲，不再共享单个 currentWebSocket 槽位，单句响应等待有三十秒上限。

聊天页对云端服务一次提交整段清理后的文本，使用 TtsSubmissionOrder 保持清理、初始化阶段发生挂起时的提交顺序。分句实际入队后即放行下一次流式提交，不等当前句播放结束。本地与系统提供方保留既有合成策略。

[自动朗读入口与语音通话朗读](../patch18-voice-call-autoread/index.md) 接续调整全屏入口：原 enqueueSpeak 已移除，改由消息处理层通过 MessageSpeechPlayback 提交分句；云端仍在实际入队后放行后句，继续使用本节的预取队列。界面文字更新与定稿不再控制播放生命周期，通话实例独立于主聊天单例。

暂停保留当前音频与预取任务，继续播放时保持顺序；停止、新的中断朗读和释放服务会取消旧准备任务与等待结果。聊天页只由当前轮次报告失败，用户停止及旧轮次的迟到结果不会额外提示合成失败。HTTP 取消会调用 Call.cancel，包含响应流水线追加的下载请求；Realtime 取消对应分句的连接。临时文件在写入失败、取消或播放结束后清理，自定义 HTTP 保留现有音频缓存，并处理同时返回与服务关闭的缓存所有权。

云端 speaking 状态覆盖排队、请求和播放阶段，暂停时仍为 false，避免尚有分句等待时提前恢复语音通话收音或隐藏朗读控制。音频完成使用播放器回调交接，旧播放器的迟到回调不能释放新播放器。日志记录各分句的序号、准备开始与耗时，不增加额外正文日志。

## 完整回归操作与预期

1. 手动朗读四句完整消息：首句音频就绪后开始播放，后续三句在首句播完前提交准备，不等待整段完成
2. 流式自动朗读：首句播放期间到达的后句立即进入预取，尚未生成的文本不会被虚构或提前请求
3. 悬浮全屏语音回复：云端后句不再等待上一句 speak 任务结束，按原文顺序朗读
4. 让第二句返回慢于第三、四句：仍按一、二、三、四播放，已完成的后句不抢播
5. 让首句响应很慢：后句等待首句准备完成才发起，首句播放不等待整段音频
6. 首句请求尚未完成时暂停、继续：暂停期间不开始播放，继续后顺序正确，已准备内容仍可用
7. 首句播放时暂停，等待其他请求完成后继续：从暂停位置继续，后续句不丢失、不重复
8. 句间有慢请求：朗读状态仍保持，控制条和语音通话不会把这一空档当成整轮结束
9. 请求与下载过程中停止：未完成请求被取消，完成的旧音频不会在停止后播放
10. 旧回复预取中开始新的中断朗读：立即切换到新一轮，旧回调不停止或释放新播放器及新连接
11. 任意句出现 HTTP 错误、超时、空音频或播放器错误：保留失败结果，停止该轮后续播放，新一轮仍可朗读
12. HTTP 返回音频 URL 或请求对象的流水线：后续下载同样可预取与取消，原有解析、鉴权和参数保持有效
13. 分别使用自定义 HTTP、OpenAI HTTP、Realtime、硅基流动、MiniMax、MiMo、豆包：模型、音色、语速及实际支持的音调参数保持原行为
14. 清理后为空的消息，以及系统 TTS、VITS 和 Sherpa：空文本不请求，本轮不改变本地与系统服务的合成策略
15. 重复分句同时返回及朗读中关闭服务：缓存不被提前删除，关闭后不遗留半成品或再次插入缓存
16. 较长消息、明暗主题和双方消息风格混搭：朗读顺序、暂停停止控制、聊天显示与分享保持正确，工作区属性仍可用
