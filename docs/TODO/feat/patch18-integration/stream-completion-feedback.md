用户在常规小文件上观察到单次读取约 10 毫秒，20 次工具调用约一秒，亚秒显示可以看到真实数值。用户另报告外层汇总与内部板块偶尔不一致，未提供发生差异时的具体数值，暂不据此修改统计口径。

## 已确认的触发规则与证据边界

5003 是 CONNECTION_ABORTED，来自系统 ECONNABORTED 或 SocketException 的标准连接中止文字。代码没有按输出 Token 数量触发该错误；首输出等待上限是十分钟，超时产生独立的 5004，收到正文或思考后即解除。网络读取等待上限是 1000 秒，不能从供应商的用量表推断手机实际收到多少内容。

## 修正范围与实施顺序

1. 在已有 transport 包增加完成状态下的行读取处理，仅协议已经确认完成、且没有客户端或协程取消时，把后续读取异常作为尾部传输结束；未完成的异常原样抛出
2. OpenAI 兼容 Chat Completions 保留结束原因之后的用量块；Responses 的 completed 和 incomplete 最终事件处理后直接退出，不再等待不存在的 DONE
3. 为每个 HTTP 请求独立记录实际交付给应用的响应体字节、OpenAI 已解析事件和输出字符，以及客户端取消状态；错误描述只增加计数与状态
4. 增加真实供应商解析入口的回归源码，保留完整 170 项设备清单并追加协议收尾与定位操作；不运行本地构建、测试或付费请求
5. 静态检查、提交原工作分支、更新中文 PR 描述并派发 Debug 与 JVM 工作流，不轮询 CI

本次不改变未完成响应的自动重试与原子撤回策略，不把部分回答伪装为成功，不改变 5003 的含义。是否解释截图中的实际失败，需要后续带进度字段的错误或对应请求日志确认。

## 已实现行为与定位字段

OpenAIProvider 在 finish_reason 之后仍读取供应商的用量块，收到用量后结束；Responses 的 completed 和 incomplete 最终事件处理完即结束。仅补读行的 IOException 且协议已经确认完成时按传输尾部结束处理，用户或协程取消继续传播。JSON 解析、服务端错误和处理回调均位于该边界之外。

SharedHttpClient 的应用拦截器记录解码后交付给应用的响应体字节，保持正文、Content-Type、长度、关闭和异常传播。每次 Call 持有自己的 RequestFailureTrace；错误上下文增加以下可选观察，不包含正文：

- responseBodyBytesRead：实际从响应体来源读取的字节，允许缓冲先于正文消费，不等于供应商生成或计费的 Token
- clientCancelled：本地 Call 是否被取消；首输出看门狗仍由 5004 说明具体发起者，false 不能据此判定是谁中止了网络
- streamEventsParsed、outputCharsParsed：OpenAI 入口已解析的事件与输出字符，字符按 Kotlin String.length 计；尚未接入此观察的协议不填零代替未知
- protocolCompleted：是否已经识别有效完成原因或最终事件；记录解析进度不能单独证明 UI 已绘制或消息已落盘

5003 的系统触发规则保持不变，没有按长输出拦截、协议切换、新增重试或重新发起付费请求。未完成响应仍遵循原重试策略，重试接受后整体撤回本 attempt，避免混合两个不同回答。
